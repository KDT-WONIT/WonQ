# WONIT 사내 자산관리

React 웹, FastAPI 업무 API, PostgreSQL, 기능별 Python 워커를 관리하는 모노레포입니다. 상세 개발 계획서의 납품·입고, 실사, 수량 재고, 알림함을 개발용 대시보드에서 확인할 수 있습니다.

## 로컬 개발

레포 루트에서 실행합니다.

```sh
docker compose -f infra/compose.dev.yml up --build
```

브라우저에서 [http://localhost:8080](http://localhost:8080)을 열고 개발용 계정을 선택합니다. 로컬에서는 네 종류의 워커가 내부 API를 통해 PostgreSQL 작업 테이블에서 작업을 가져옵니다. AWS 계정과 모델 API 키 없이 아래 흐름을 실행할 수 있습니다.

1. **외부업체** 계정에서 납품 요청을 만들고 개별 자산이나 수량 재고를 품목으로 추가합니다.
2. **부서 담당자** 계정에서 납품 목록을 열고 승인 수량을 검토합니다. 개별 자산 라벨은 승인 후 내려받을 수 있습니다. 현장에서 수령 수량과 검수 합격 수량을 기록하고 차이가 있으면 사유를 적습니다.
3. **외부업체** 계정에서 검수 결과를 보고 이름으로 인수 확인합니다. **부서 담당자** 계정이 입고를 확정하면 합격분이 자산·재고와 변동 이력에 반영됩니다.
4. **부서 담당자**가 실사 회차를 시작하면 현재 장부값이 기준값으로 저장됩니다. QR 또는 대상별 확인 입력으로 실사하고 결과를 제출합니다. **구매 담당자**가 결과를 확정할 수 있습니다.
5. 수량 재고에서 안전재고 기준과 지급·공정 소모를 기록합니다. 안전재고 미달 알림은 구매 담당자 알림함에 표시되며, 읽음 상태는 계정별로 기록합니다.

개발 DB에서 통합 검증을 재현할 수 있습니다. 실행할 때마다 테스트용 납품·실사 데이터가 추가됩니다.

```sh
python tests/smoke.py
```

```sh
docker compose -f infra/compose.dev.yml down
```

로컬 PostgreSQL 데이터는 Docker 볼륨에 보관합니다. 새 볼륨에는 마이그레이션만 적용하며 기존 볼륨의 데이터는 보존합니다. 이전에 샘플 데이터나 테스트 데이터를 저장한 볼륨에는 그 기록이 표시됩니다.

## 업무 화면

`WonQ.html`의 고정 사이드바, 하위 메뉴, 상단 검색·알림, 대시보드 카드, 자산 표와 도우미 창을 React로 옮겼습니다. 통합 검색의 자산 탭, 알림함, 납품·입고, 재고, QR 조회, 실사는 기존 업무 API를 사용합니다. 대시보드의 실사 지표는 권한 범위 내에서 가장 최근 시작한 회차의 현장 확인 대상만 집계합니다. 아직 한 건도 현장에서 확인하지 않았으면 지표는 공란입니다.

공지·층별 도면·핵심 자산·보고서·담당자 검색·챗봇 화면은 미연결 상태입니다. 해당 콘텐츠를 채우는 예시 레코드나 예시 응답 없이 빈 상태를 표시합니다.

## 레포 구조

| 경로 | 역할 |
|---|---|
| `apps/web/` | React·TypeScript 화면, ZXing-JS QR 스캔, Nginx |
| `backend/` | FastAPI, JWT 검사와 부서 범위, 자산·작업 API, Alembic |
| `ai-service/` | 챗봇·보고서·실사·모니터링 워커와 SQS 수신 |
| `contracts/` | 큐 메시지 v1과 백엔드·워커 공용 타입 |
| `infra/` | 로컬, 회사 서버, AI EC2용 Compose 설정 |

## 데이터베이스 변경

상세 개발 계획서의 DB 슬라이드에 맞춰 업무 영역을 나눴습니다. 로컬 Compose의 `migrate` 서비스가 `alembic upgrade head`를 실행합니다.

| 리비전 | 구조 |
|---|---|
| `0001` · `0002` | 자산과 AI 작업, 납품 요청·품목·검수 수량, 재고·변동, 실사 회차·대상, 알림·읽음 |
| `0003` | 품목·부서·위치·업체·사용자 기준정보와 공지. 기존 원장에는 선택적인 기준정보 참조를 추가 |
| `0004` | 자산 작업·권한 변경 요청, QR 발급·재발급 이력, 실사 후속 조치, 설비 구성·정비, 수요 예측, 보고서·버전의 기본 테이블 |

조회 범위와 기존 이력은 현재 업무 API와 호환되는 부서 코드·위치 문자열로 유지합니다. 매핑을 확정한 뒤 새 리비전에서 ID를 채우고 조회와 권한 검사를 전환할 수 있습니다. 품목 외형 속성이나 예측 산출 근거처럼 형식이 정해지지 않은 부가 데이터에만 JSONB를 사용합니다.

컬럼을 확정할 때는 SQLAlchemy 모델을 수정하고 새 Alembic 리비전을 만듭니다. 기존 행에 필수 컬럼이 필요하면 컬럼 추가, 기존 행 채우기, 제약 적용 순으로 진행합니다. 기존 리비전과 이미 저장된 장부를 보존하는 방식입니다. `0004` 테이블을 사용하는 화면과 업무 API, 파일 저장 참조, 로트 단위 재고는 별도로 연결해야 합니다.

## 작업 흐름

- `POST /api/jobs`로 작업을 등록하고, `GET /api/jobs/{id}`로 본인 작업의 상태와 결과를 읽습니다.
- SQS 모드에서는 회사 서버의 발행기가 DB에 저장된 요청을 종류별 큐로 보냅니다. 큐 메시지에는 `schema_version`, `job_id`, `kind`가 포함됩니다.
- 워커는 인증된 내부 API에서 자기 종류의 작업과 허용 범위의 데이터를 받아 결과를 반환합니다. 작업 선점과 결과 갱신은 DB에서 처리하며, 이전 실행의 응답이 새 실행 결과를 덮어쓰지 않도록 실행권을 검사합니다.
- PostgreSQL은 업무 API와 발행기가 사용합니다. 기본 SQLAlchemy 풀은 프로세스당 상시 5개, 추가 2개입니다. AI 워커는 업무 API를 사용합니다.

## 배포 골격

CI에서 레포 루트를 빌드 컨텍스트로 사용하고, 대상 서버의 CPU 아키텍처에 맞춰 Docker 이미지를 빌드합니다. 회사 서버에는 웹·백엔드 이미지를, AI EC2에는 워커 이미지를 배포합니다. 현재 워커 Dockerfile은 네 가지 작업을 지원하며 Compose의 `WORKER_KIND`가 실행 종류를 지정합니다. 네 서비스에 동일한 이미지 태그를 사용하거나 각자 태그를 지정할 수 있습니다.

1. 회사 환경에 별도 PostgreSQL, AWS에 기능별 Standard SQS 요청 큐 4개를 준비합니다. 회사 서버 발행기에 큐 전송 권한, AI EC2에는 수신과 삭제 권한을 부여합니다. 반복 실패 메시지를 조사하려면 각 큐에 DLQ를 연결합니다.
2. 회사 서버와 AI EC2에서 각각 `infra/.env.backend.example`, `infra/.env.ai.example`을 복사해 실제 주소·이미지·인증 값을 설정합니다. 양쪽의 워커 토큰은 일치해야 합니다. AI EC2의 `BACKEND_API_URL`은 승인된 사내 연결을 통해 회사 서버의 내부 업무 API에 접근할 수 있는 주소로 지정합니다.
3. 회사 서버에서 배포합니다. 웹과 내부 API의 기본 바인딩은 루프백이며, 회사 HTTPS 게이트웨이에서 웹과 내부 연동 경로를 구성합니다.

```sh
docker compose --env-file infra/.env.backend -f infra/compose.backend.yml pull
docker compose --env-file infra/.env.backend -f infra/compose.backend.yml run --rm backend alembic upgrade head
docker compose --env-file infra/.env.backend -f infra/compose.backend.yml up -d
```

4. AI EC2에서 배포합니다.

```sh
docker compose --env-file infra/.env.ai -f infra/compose.ai.yml up -d --pull always
```

`CHATBOT_REPLICAS=2`를 `3`으로 바꾸면 챗봇만 3개로 실행합니다. 나머지 워커는 각 1개입니다.

## 다음 구현 범위

- 로그인은 개발 계정 선택으로 시작합니다. Auth0, 사내 계정 디렉터리 및 시스템 관리자 권한 변경 절차를 연결해야 합니다.
- 납품은 수동 입력·검수와 이름 입력 인수 확인까지 지원합니다. 명세서·사진 업로드, S3/MinIO 보관, 서명 이미지, OCR·Vision, 반려 후 재제출, QR 교체 이력은 후속 구현 범위입니다.
- 수량 재고는 정수 수량의 입고·지급·공정 소모를 지원합니다. 로트·포장 환산·위치 이동, 개별 자산 대여·반출·폐기, 정비·실사 후속 조치 이력은 후속 구현 범위입니다.
- 챗봇과 보고서 워커는 샘플 응답을 반환합니다. 실사 워커는 불일치 목록을, 모니터링 워커는 현재 안전재고 미달 항목을 반환합니다. 실제 LLM API·PDF·수요 예측·n8n 발송은 아직 연결되지 않았습니다.
- 계획서에 RabbitMQ가 표기되어 있습니다. 이 구현의 배포 설정은 기존에 합의한 SQS 요청 큐 4개를 기준으로 작성했습니다. 운영 브로커를 확정하면 배포 설정과 메시지 연동을 함께 점검해야 합니다.
